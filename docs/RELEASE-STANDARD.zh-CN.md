# Release 工程与发行资产规范

**简体中文** · [English](RELEASE-STANDARD.md)

状态：2026-11-03 起作为全产品家族的**目标验收规范**。它不是已有发行版都已通过验收的证明。修改发布流程前，应阅读[产品交付标准](PRODUCT-STANDARD.md)、[分发与签名政策](DISTRIBUTION.zh-CN.md)、[产品组合](../PORTFOLIO.zh-CN.md)以及项目本身的更新协议。不能为了形式统一破坏已发布的签名更新清单、第三方插件商店约定或草稿发布门槛。

## 项目类型与资产

| 类型 | 应发布 | 不应发布 |
| --- | --- | --- |
| 桌面应用 | 已构建并通过验收的平台/架构安装器及便携包、一份已核验的校验清单、必需的签名更新信息及合法授权/供应链文件 | `.wixpdb` 调试文件、构建中间产物、无版本号重复副本、已由 `SHA256SUMS` 完整覆盖的逐件校验副本 |
| 命令行工具 | 可独立运行并按架构区分的压缩包或可执行文件、必要的校验信息 | 并未实现的 GUI 安装包 |
| Racket 库/框架 | 可通过 Catalog 或经测试的源码包、变更记录及合理的校验/签名；示例安装器明确标注为展示程序 | 虚构桌面平台或强行套用应用安装包矩阵 |
| Obsidian 等第三方插件 | 遵循其安装器要求的文件、版本标签和实际运行时依赖 | 破坏插件生态约定的强行改名、删除必需文件 |
| 尚无合格发布 | 清楚描述未通过的构建/验收门槛 | 假装有可安装软件的 Latest 按钮 |

DMG、MSI、DEB、RPM、AppImage、ZIP/tar.gz、Flatpak 只有在确实受支持且有安装/升级证据时才应发布。保留原生构建工具要求的架构语法：DEB 常见 `amd64/arm64`，RPM/AppImage 常见 `x86_64/aarch64`，便携包可能为 `x64/arm64`；RPM 还可能带独立发行修订号。不要只为看起来统一而错误改名。

## 名称、版本与用户可见内容

- 首选标签 `v主版本.次版本.补丁版本`；明确标注 RC/预发布。第三方插件商店强制要求的标签方式优先。标签、软件内部版本、包元数据及变更记录必须一致。
- 常规命名为 `<项目名>-<版本>-<系统>-<架构>.<扩展名>`，保留实际格式需要的修订号和独立 CLI、GUI、更新载荷区分。使用小写 ASCII 名称，不随意修改 `.AppImage` 等大小写敏感扩展名。
- 页面标题采用 `Product X.Y.Z`，不要只堆标签。发布说明要有真实变更、支持范围、限制以及适用时的签名状态。GitHub 自动生成的 Source code 并非已测试可安装的软件。
- 更新器应使用精确标签下的不可变资产 URL。官网不能继续指向已删除的 `releases/latest/download/<无版本号别名>`。可按最新正式版 API 校验对应资产后直达下载，失败时回退到普通 Release 页面，而非错误架构或失效直链。

## 强制发行检查

1. **发布前**核对标签、提交 SHA、完整允许列表、唯一文件名、非空体积、准确系统/架构/格式、实际 SHA-256、适用时的签名更新清单和可访问的版本化地址。多余文件和缺失文件都应阻断发布。
2. 以确定性文件排序生成一份 `SHA256SUMS`，并在**最终公开资产目录**内验证，保证已发布的文件可独立校验。单件 `.sha256` 可保留在 CI 诊断产物；真正需要的 `.sig`、公钥和第三方声明不能当成重复校验文件删除。公开 SBOM、声明同样应获得校验。
3. 只允许显式白名单上传。密钥、WiX 调试/中间文件、临时二进制和内部日志留在 CI，不得公开泄漏。重试只能处理准确匹配的标签或草稿，不能误删其他版本。
4. 已公开版本的字节必须维持不可变；如载荷发生变化，应提高版本号，而不是覆盖旧版签名资源。稳定版、RC、草稿和 Latest 各自遵守渠道约定。
5. 代码构建成功不代表安装成功。每种支持的安装形式需要干净安装、首次运行、N→N+1 升级、取消及断电/异常恢复、用户数据保留、错误签名/摘要拒绝和卸载测试。未有这些实测证据不得强行通过发布门槛。
6. 未取得 Apple 公证或 Windows 发布者签名时，应明确标记开发/评估版；Ed25519 更新清单不等于操作系统信任安装器。不得降低生产签名、Store 或审批门槛来制造“完整”的 Release。
7. 验证官网、README、中英文安装指引的每个下载入口都和实际 Release 资产匹配；不要仅仅在 GitHub 上删除别名却留下官网 404。
8. 有条件时对最终公开资产提供构建来源证明；禁止在产物中泄露签名私钥、支付密钥、用户身份信息。

## PR 验收证据与历史版本

每个产品 PR 应记载：起始提交 SHA、所采用的中央规范版本、项目类别、核查的标签和真实资产、更新器/官网兼容性影响、CI 结果、仍待完成的原生平台实测及预计使用新规范的下一版本。

**发布流水线合并成功 ≠ 新安装包已生成并跨平台验证。** 历史版本不应仅为了外观一致被批量重写；签名清单、第三方索引和用户下载可能依赖其不可变内容。即使目前用户很少，涉及破坏性迁移也必须记录并对下一版实测。
